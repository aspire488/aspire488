PipoPipo

Pipo is an Android app about a small robot who lives his own day. It is Kotlin and Jetpack Compose on a deterministic life simulation: ten personality traits, twelve moods, persistent memory, and the time you were away replayed when you open it. The 3D room on the web is a separate three.js project in the same repository.

shipped, v1.0 (2026-10-04)

Tried on one phone so far: a Samsung Galaxy S23.

Why it exists

You don't manage him. You drop in and discover what happened.

From the README. Its engine notes say the same in code terms: elapsed time is reconciled when Pipo returns, and no always-running server is required.

What I built

Built solo: the simulation engine, the Compose and Canvas renderer, the toddler voice and wake word, the chat brain and its Cloudflare proxy, the three.js web room, the tests, and the CI workflows.

GitHub lists one contributor on the repository.

How it's put together

  • Simulation core engine/Personality, mood, behaviour, trips, the world, games, conversation and grounding. Under app/src/main/java/com/pipo/robot/. It runs in local unit tests, no device needed.
  • Saved state data/One PipoState in one JSON file, written through a temp file and a rename. Migrations upgrade old saves, and the old file is kept beside the new one as a .bak.json.
  • Renderer ui/render/PipoPainter, RoomPainter, PetPainter, Rig and the other painters draw everything on the Compose Canvas, lit by time of day.
  • Voice voice/ToddlerVoice shifts an adult text-to-speech voice. WakeModel fetches the offline Vosk model behind the "Pipo" wake word. VoicePolicy decides when the listener may hold the microphone.
  • Chat ai/, server/worker.jsChatBrain tries Gemini, then Groq, then falls back to his offline words. Store builds call a small Cloudflare Worker that holds the keys.
  • Background notify/PipoWorker.ktWorkManager wakes roughly hourly, replays his life, and may let him send one message about something that happened.
  • Phone actions engine/PhoneCommands.kt, lock/PipoLock.ktCommands you ask for: torch, volume, apps, alarms (after a confirmation). Pipo lock uses the platform's force-lock device admin.
  • Web room web/A three.js 0.169 scene served from GitHub Pages. web/classic is the original 2D world.

Decisions, and why

  1. No background process: the time you were away is replayed in 40-minute steps, up to three days.

    Simulator.kt says nothing runs continuously. When the app or the hourly worker wakes, the same behaviour engine replays the gap, then saves.

  2. The AI only voices Pipo.

    ChatBrain keeps the local engines as the source of truth, and the AI keeps any action the offline brain chose. The offline reply is the fallback whenever the network or a provider fails. Grounding.kt feeds both from saved state, so "what did we do yesterday?" gets the real day.

  3. Provider keys are blanked in release builds and live in a proxy.

    The build file says anything in an APK can be pulled out by whoever has the file. The proxy only allows the models and endpoints Pipo uses and rate-limits per install, but its README is plain that those limits are abuse controls, not authentication.

  4. The wake-word model is downloaded once, and only accepted if its SHA-256 matches.

    A tampered or truncated file is thrown away. The model runs on the phone and nothing is uploaded.

  5. His voice is made by shifting playback, not only pitch.

    Raising text-to-speech pitch alone gives a chipmunk man. The line is rendered slowly at a raised pitch, then played 1.45x faster, which scales pitch and formants together.

  6. Pipo lock uses the platform's force-lock policy, not an accessibility service.

    Nothing reads the screen, apps or typing, and Android shows its own activation screen before anything works.

The interesting problems

  • Colour blending was the hottest path

    simpleperf on the S23 showed Compose's lerp(Color, Color) converting through Oklab dozens of times a frame. ColorMath.lerp blends packed sRGB instead. Release frame time went from p50 13 ms to 11 ms and p90 20 ms to 16 ms (dumpsys gfxinfo).

  • A project retry loop

    After a retry had evolved a project into something else, he "tried again" from scratch and attempt numbers went backwards: the retry candidate ignored later attempts. Fix: retry only when the latest attempt failed, covered by three tests and a two-week simulation.

  • The first line after a cold start was silent

    His mouth moved and nothing played, because the speech engine was still initialising (over 3 s). Speech now waits for voice.ready, up to 8 s.

  • A carried Pipo drifted from the finger

    About 120 px, because the camera kept re-centring on him during the drag. The camera now holds during a carry and edge-scroll takes him along.

How it's tested

Last verified run (device report, 2026-09-29): 68/68 JVM unit tests across 11 test classes, 6/6 instrumentation tests (PoseGalleryTest) on the S23, lint 0 errors and 12 warnings. Last CI run on main (2026-11-05): 226 tests, 1 failed.

The failing one is GroundedLifeTest > askedToShopLateHeNeverWandersOffToTheGarden. Counting @Test in app/src/test gives 226 across 31 files, so the suite has grown since the device report. ./gradlew testDebugUnitTest; ./gradlew assembleDebug. build-apk.yml runs both on every push and uploads the debug APK and test reports. LongLifeSimulationTest runs six seeded personalities through two weeks, hour by hour, on the real engine, and fails on retry loops. On the S23 I also checked process death and relaunch, home and return, and screen-off and unlock.

Limits I've written down

  • One phone, at 60 Hz. Battery drain, a thermal soak and a 120 Hz mode were not measured.
  • CPU use is about 0.9 of one core in release: fine for a foreground character app, not small. Caching the static parts of the room into a layer is the noted next step.
  • Mouth timing is estimated from speech rate, not synchronised with the audio.
  • Chat needs your own Gemini or Groq keys at build time, or a proxy. Builds without keys, like CI, use the offline brain.
  • Notification noticing was tested with ADB-posted stand-ins for real third-party messages, and the hourly worker by running the same code on demand.
  • The device report covers the build before the trips, Nib, weather and map update. docs/FEATURE_HISTORY.md marks later features as seen on the phone, but there is no full report for them.
